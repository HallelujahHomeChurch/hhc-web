# 服事表管理者訪談指南

## 訪談目的

了解主要管理者目前如何收集、安排、發布與調整服事，以及一般會員實際需要查找哪些資訊。訪談結果用來驗證與修訂 `spec.md`，不預設目前規劃的畫面或資料結構一定正確。

## 訪談前準備

- 建議每位主要管理者分開訪談 45–60 分鐘；若多人共同負責，可另安排一次對照討論。
- 請受訪者先描述最近一次實際排班，再討論理想做法。避免一開始展示規格或詢問「清單和月曆哪個比較好」，以免把回答帶向既有方案。
- 邀請受訪者準備一份近期排班表、使用中的服事項目／人員名單，以及一個最近發生的臨時變動案例。分享前可移除不必要的個人聯絡資訊。
- 記錄「目前怎麼做」、「遇到什麼問題」、「想改善什麼」和「哪個角色有權決定」；把現行做法與新系統需求分開記。

## 建議訪談流程與問題

### 1. 角色與責任

1. 請介紹你在安排服事中的角色，以及你負責哪些聚會或服事項目。
2. 還有哪些人會提供名單、排班、確認或發布安排？誰負責最後決定？
3. 不同聚會、部門或服事項目是否由不同管理者負責？各自負責範圍如何交接？
4. 如果主要管理者不在，誰會代理？代理時需要哪些權限與資訊？

### 2. 從需求到發布：走一次最近的排班流程

請受訪者以最近一次排班為例，從「開始準備」一路說到「服事者知道安排」：

1. 通常何時開始安排？一次安排多久、涵蓋幾場聚會？固定多久重排一次？
2. 你從哪裡知道接下來有哪些聚會、需要哪些服事崗位？這些資訊由誰提供？
3. 你先建立聚會，還是先依服事崗位排人？請依實際順序描述每一步。
4. 目前用哪些工具或檔案？哪一份是大家認定的最新版本？如何讓服事者找到它？
5. 排班完成後需要誰檢查或核准？何時算正式發布？
6. 請舉一個最近一次從開始安排到發布所花的時間，以及最花時間的步驟。

### 3. 聚會、崗位與人員資料

1. 一份服事表裡，最基本的安排單位是什麼？例如一場聚會、一個時段，還是某個服事崗位？
2. 每場聚會目前會記錄哪些資料？哪些資料缺了就無法安排或讓服事者準時到場？
3. 一場聚會可以有多個服事崗位嗎？同一崗位可能需要幾個人、幾位負責人或一個小組？
4. 崗位是否有固定名稱、說明、地點、報到時間或服裝／器材要求？哪些內容會變動？
5. 服事人員如何選出？是否只能選教會會員？兒童、家庭、小組或臨時支援人員如何處理？
6. 同名、改名、停會籍或暫停服事時，現在如何確認是同一個人或更新名單？
7. 有些崗位是否會先空缺、稍後補人？若可以，會員看到空缺時應看到什麼？
8. 同一人同一時段被排在多個崗位時，現在如何發現與處理？

### 4. 排班規則與例外

1. 安排人員時會遵守哪些規則？例如資格、訓練、輪值、公平分配、不可同時出席或固定搭檔。
2. 管理者如何知道某人不能服事、偏好某時段或已排了其他服事？這些限制要不要記在系統？
3. 哪些規則必須由系統阻止，哪些只需要提醒管理者，哪些仍由管理者自行判斷？
4. 有沒有常見的臨時狀況，例如聚會取消、時間更改、臨時增加崗位或人員請假？請說明最近一次怎麼處理。
5. 不同服事項目的排班規則是否不同？請舉出不能用同一套規則處理的例子。

### 5. 編輯、確認與紀錄

1. 哪些人可以新增聚會、調整崗位、指派人員或刪除安排？這些權限是全教會共用還是按聚會／服事項目分開？
2. 編輯者需要自己指派，還是要經另一位管理者確認後才能發布？哪些修改必須再次確認？
3. 多人同時編輯時如何避免互相覆蓋？是否需要顯示最後修改者與修改時間？
4. 刪錯或取消聚會時，需要復原嗎？應保留哪些歷史紀錄、由誰可查看？
5. 哪些資料可以直接移除，哪些需要保留在過去排班中供查詢？
6. 如果同一場聚會需要複製上一週安排，現在會怎麼做？哪些資料通常要保留、哪些一定要重新確認？

### 6. 會員如何查看服事表

先請受訪者描述會員常問的問題，再追問可能的呈現方式：

1. 會員最常想知道什麼？請列出他們查表時會問的前三個問題。
2. 會員通常想先看自己被安排的服事，還是需要看全教會所有服事？他們會不會需要同時查看別人的安排？
3. 通常要提前多久查看？過去的排班需要保留多久、哪些人會查？
4. 會員會用手機、電腦或列印版？在哪些場合查表？
5. 月曆、依日期排序的清單、搜尋或篩選各自能解決什麼問題？請用最近實際查找的例子說明。
6. 需要按聚會、日期、崗位、人員或部門查找嗎？哪些條件最重要？
7. 會員是否需要列印、匯出、加入個人行事曆或分享連結？如果需要，誰可以分享給誰？
8. 哪些內容適合所有有效會員查看？是否有不應顯示的聯絡資料、備註或個人資訊？

### 7. 通知需求（後續階段；先了解問題，不承諾第一階段）

1. 現在如何通知服事者新安排、變更或取消？使用哪些通路？哪個方式最常漏掉？
2. 哪些事件真的需要通知？建立、發布、指派、調整時間、人員更動、取消，還是全部？
3. 通知應寄給當事人、整個崗位、小組負責人，還是其他人？同一人有多個崗位時希望收到幾封？
4. 通知要在什麼時間送出？即時、固定提前量、定期彙整，或由管理者手動發送？請描述最理想和不可接受的情況。
5. 服事者需要確認收到或回覆是否能出席嗎？沒有回覆時由誰跟進？
6. 通知寄送失敗、信箱錯誤或當事人不常看 Email 時，管理者希望怎麼處理？
7. 是否需要避免在通知中暴露其他服事者的個人聯絡資料？

### 8. 調動、認領與交換（後續階段）

先了解真實痛點，不先指定解法：

1. 服事者需要換班時，目前如何提出？通常由誰找替代者、誰確認最後安排？
2. 什麼情況下可以由別人直接認領空缺？認領後是否需要管理者核准？
3. 交換兩場服事是否常見？交換雙方需要符合哪些資格、時間或崗位條件？
4. 有人提出請求後，在核准前原本安排是否仍有效？誰能取消或撤回請求？
5. 同一空缺多人認領或兩人同時交換時，如何決定先後？
6. 沒有人承接、請求逾期或聚會取消時，管理者希望系統如何提醒與呈現？
7. 從提出需求到完成交接，哪些人需要收到通知？何時通知？

### 9. 優先順序與驗收

1. 如果第一版只能解決三件事，哪三件最重要？為什麼？
2. 哪些需求可以晚一個階段？哪些若沒有就無法開始使用？
3. 上線後怎麼判斷真的改善了？例如少花多少時間、少幾次錯排或少幾次會員詢問。
4. 請描述一個你會用來驗收的完整情境：「我做了什麼，系統應該顯示／完成什麼」。
5. 你還擔心什麼目前沒有談到？哪些決定需要再找其他人確認？

## 訪談後整理

- 將現行流程與建議的新流程分開畫出，標明每個步驟的執行者、輸入、結果及例外。
- 將需求標記為「多位管理者共同需要」、「特定服事項目需要」或「尚待決策」，避免用單一受訪者的做法代表全教會。
- 回到 `spec.md` 逐項標記為已驗證、需修訂或仍待決策；特別重新檢查資料結構、檢視方式、編輯／刪除權限、未來排班範圍及通知邊界。
- 形成可驗收的情境與測試資料，再更新 spec 的驗收條件；未經管理者確認的建議不直接轉成需求。
