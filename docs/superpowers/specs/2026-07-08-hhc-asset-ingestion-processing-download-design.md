# HHC Asset Ingestion, Processing, And Download Pipeline Design

This spec defines the lower-level asset pipeline behind `asset-api`: upload target issuance, upload completion validation, Blob key layout, malware scanning, derivative generation, quarantine, download streaming, range requests, headers, retries, and operational recovery.

## Purpose

`asset-api` is reusable only if the byte-handling path is safe and boring. Weekly PDFs, CMS images, LINE group files, and future desktop-folder objects should share the same upload, scan, process, store, and download mechanics without sharing business meaning.

Public image derivative, dimensions, Open Graph image, and performance delivery expectations are specified in the public web accessibility/performance/media design.

This design prevents:

- public download before scan/processing is safe
- Blob/SAS URL leakage
- oversized file exhaustion
- MIME spoofing
- duplicate upload completion bugs
- derivative permission drift
- stale public downloads after grant revocation
- orphan Blob objects after failed uploads

## Core Decision

Use `asset-api` as the only service that owns platform-managed Blob storage. Consumers can request upload sessions and stable gateway URLs, but they cannot build storage keys, expose Blob URLs, or bypass scan/processing state.

Upload and processing are state-machine driven:

```text
upload session created
  -> bytes uploaded to short-lived target
  -> completion validation
  -> asset metadata created
  -> scan worker
  -> derivative/processing worker
  -> downloadable when policy allows
```

## Storage Layout

Use environment-specific containers or prefixes. Never mix production and non-production objects.

Recommended Blob key shape:

```text
{env}/{namespace}/{yyyy}/{mm}/{assetId}/original
{env}/{namespace}/{yyyy}/{mm}/{assetId}/derivatives/{kind}
{env}/{namespace}/{yyyy}/{mm}/{assetId}/quarantine/original
```

Rules:

- Blob key must be generated by `asset-api`.
- Do not include raw user filenames in Blob keys.
- Store sanitized `displayFileName` in metadata only when needed.
- Store checksum and size in PostgreSQL.
- Blob metadata can duplicate non-sensitive operational fields, but PostgreSQL remains authoritative for state.

## Upload Modes

### Browser Direct Upload

Use for CMS admin files when proxying bytes through application containers is unnecessary.

Flow:

1. Admin UI calls `www.alive.org.tw/api/assets/admin/upload-sessions`.
2. Gateway validates JWT and route scope.
3. `asset-api` validates namespace policy, owner service, MIME hint, max size, and caller permissions.
4. `asset-api` creates session and returns a short-lived upload target.
5. Browser uploads bytes to the target.
6. Browser calls complete endpoint through gateway.
7. `asset-api` validates actual object properties and creates asset metadata.

Upload target rules:

- TTL defaults to 10 minutes for admin CMS.
- Scope target to one object key only.
- Limit permitted method to upload/write for that object.
- Limit max size where the storage provider supports it.
- Never allow list/read/delete permissions in browser upload target.
- Do not log upload target URL.

### Service-Mediated Upload

Use when the caller service already holds the bytes, such as LINE bot saving a file from LINE content API.

Flow:

1. Caller service invokes `POST /priv/assets/upload-sessions`.
2. `asset-api` verifies caller app id and namespace allowlist.
3. Caller uploads bytes to the issued target.
4. Caller completes the upload with checksum and size.
5. `asset-api` validates and queues scan/processing.

The caller service still does not receive broad Blob credentials.

### Proxy Upload

Use only for small files or early development.

Rules:

- `asset-api` still owns the final Blob object.
- Enforce the same namespace size/MIME policies.
- Disable proxy upload for large files to protect app replicas.
- Prefer direct upload for files above the configured in-memory/body threshold.

## Upload Session Schema

Upload session should include:

- `session_id`
- `asset_id`
- `owner_service`
- `owner_type`
- `owner_id`
- `namespace`
- `object_key`
- `expected_mime_type`
- `max_size_bytes`
- `status`
- `upload_url_expires_at`
- `idempotency_key`
- `created_by_actor`
- `created_by_service`
- `created_at`
- `completed_at`
- `failure_reason`

Completion is idempotent when `session_id`, `asset_id`, size, checksum, and MIME match the first successful completion.

## Completion Validation

`POST /priv/assets/{assetId}/complete` or an admin complete route must verify:

1. Session exists and is not terminal.
2. Caller owns the session or is allowlisted for the namespace.
3. Upload target has not expired.
4. Blob object exists at expected key.
5. Object size is greater than zero and within namespace max.
6. Server-observed size matches caller-provided size.
7. Server-computed SHA-256 matches caller-provided checksum when feasible.
8. Server-detected MIME type is allowed by namespace.
9. File extension, if stored, is compatible with detected MIME type.
10. Metadata row is inserted with `scan_status=pending`.

If checksum cannot be computed during completion because of provider constraints, queue checksum calculation before scan and keep download denied until validation finishes.

## MIME And Content Validation

Do not trust:

- browser-provided MIME type
- file extension
- original filename
- provider content type alone

Use server-side content sniffing. For v1:

- PDF must match PDF magic/header and namespace policy.
- JPEG/PNG/WebP must match decoder validation.
- Reject HTML/SVG as CMS image unless an explicit SVG sanitization policy exists.
- Reject archives by default unless a future namespace explicitly supports them.

Public CMS assets must not use `scan_status=skipped`.

## Scan Pipeline

Scan is a worker-owned state transition.

Suggested states:

```text
pending -> scanning -> clean
pending -> scanning -> infected
pending -> scanning -> failed
failed -> pending       // operator retry or worker retry policy
```

Rules:

- No public/protected download while `pending`, `scanning`, `infected`, or `failed`.
- `infected` assets are quarantined or access-denied according to namespace policy.
- Scan worker uses leases so multiple replicas do not scan the same asset concurrently.
- Scan result writes audit events for clean, infected, failed, and override.
- Scan override requires elevated admin/service permission and audit.

Provider choice is implementation-specific. Start with an adapter interface so local/dev and Azure production can differ:

```text
Scanner.Scan(ctx, objectRef) -> clean | infected | failed
```

Do not make scanner output the only source of truth. Store accepted scan result in PostgreSQL.

## Quarantine

Infected files should not be downloaded.

Recommended v1 behavior:

- Mark `scan_status=infected`.
- Remove active public/protected grants or make authorization deny regardless of grants.
- Optionally move object to quarantine prefix if the provider workflow supports it.
- Keep minimal metadata for incident review.
- Emit audit event.
- Alert on infected public CMS asset.

Do not automatically delete infected files before incident review unless the namespace policy explicitly says so.

## Processing And Derivatives

Processing is separate from scanning.

Image namespaces can require derivatives:

- `thumbnail`
- `card`
- `hero`
- `webp`
- future responsive sizes

Rules:

- Derivative worker starts only after scan is clean.
- Derivatives inherit original asset grants and visibility.
- Derivative URLs go through gateway routes, not Blob URLs.
- Public image publish should require `processing_status=ready` if the projection references derivatives.
- Weekly PDFs use `processing_status=not_required` after scan.
- Failed derivative generation keeps public image publish blocked unless namespace permits original-only fallback.

Derivative records should include:

- `asset_id`
- `kind`
- `object_key`
- `width`
- `height`
- `mime_type`
- `size_bytes`
- `checksum_sha256`
- `created_at`

## Download Authorization

All download routes evaluate policy before streaming bytes.

Required order:

1. Asset exists.
2. Asset is not soft-deleted.
3. Namespace allows route.
4. Scan status allows download.
5. Processing status allows requested original/derivative.
6. Visibility and grant allow caller.
7. Rate limits and abuse controls allow request.
8. Response headers are generated.
9. Bytes stream from Blob through service or trusted internal redirect.

Public denied responses should prefer `404` to avoid asset id enumeration.

## Download Delivery

V1 can stream through `asset-api` for simplicity and policy control.

Acceptable delivery modes:

- service streams Blob bytes to client
- gateway/internal redirect to short-lived private Blob URL that is never exposed to the browser
- CDN origin pulls through gateway/asset route when cache policy exists

Do not:

- redirect public clients to Blob SAS URLs
- expose storage account hostnames as stable public URLs
- let Next.js serve platform-managed binary assets directly

## Download Headers

Set headers deliberately.

Recommended public download headers:

```text
Content-Type: <detected mime>
Content-Length: <size when known>
Content-Disposition: inline; filename="<safe filename>"
Cache-Control: public, max-age=300
ETag: "<assetId>:<assetVersion>:<checksum>"
Accept-Ranges: bytes
X-Content-Type-Options: nosniff
```

Rules:

- Sanitize filenames for `Content-Disposition`.
- Use `attachment` for namespaces that should not render inline.
- Support `Range` for PDFs and larger files when streaming implementation can do it safely.
- Do not include internal storage key, Blob URL, SAS token, or original unsafe filename in headers.
- Use shorter cache TTLs for revocation-sensitive protected assets.

## Range Requests

PDF viewers often use range requests.

Rules:

- Support single-range requests for public PDFs when feasible.
- Return `206 Partial Content` with `Content-Range`.
- Reject multi-range requests initially unless explicitly implemented.
- Apply authorization before range processing.
- Ensure range errors do not reveal private asset existence on public routes.

## Cache And Revocation

Asset URLs are stable, but authorization is dynamic.

Rules:

- Public assets can be cacheable only after clean scan and public grant.
- Grant revocation must make the asset route deny even if a content projection still references the URL.
- For assets likely to be revoked, keep short `max-age`.
- For immutable public historical PDFs, a longer CDN TTL can be considered after operational evidence exists.
- Do not use long-lived cache for protected or restricted assets.

## Worker Reliability

Workers required:

- upload session expiry cleanup
- orphan Blob cleanup
- checksum validation when deferred
- scan worker
- derivative worker
- retention/hard-delete worker

Worker rules:

- Use DB leases.
- Use idempotent transitions.
- Record retry count and next attempt time.
- Dead-letter after bounded retries.
- Expose backlog and oldest age metrics.
- Provide operator retry for failed scan/processing.

## Failure Modes

| Failure | Behavior |
| --- | --- |
| Upload target expires before completion | mark session expired; cleanup object if present |
| Blob exists but no session completion | orphan cleanup after grace period |
| Completion checksum mismatch | reject completion; mark session failed or allow retry with same object when safe |
| MIME mismatch | reject completion; asset not created or marked failed |
| Scanner unavailable | keep `scan_status=failed` or retry pending; deny download |
| Infected file | mark infected, deny all downloads, audit, alert |
| Derivative generation fails | mark processing failed; block public image publish unless policy allows original-only |
| Blob unavailable during download | return `503`; do not change grants or metadata |
| Grant revoked while cached | route denies on uncached checks; short cache TTL limits stale client cache |

## Local Development

Local/dev can use:

- local filesystem or Azurite-compatible Blob adapter
- no-op scanner that marks clean only under explicit local profile
- fake derivative generator

Rules:

- Default production/staging config must not use no-op scanner.
- Tests should include a fake scanner that returns clean, infected, and failed.
- Local upload targets must still avoid broad credentials in logs.

## Observability

Metrics:

- upload sessions created/completed/expired/failed
- upload completion validation failures by reason
- scan queued/scanning/clean/infected/failed
- derivative queued/ready/failed
- download allowed/denied by route and reason
- Blob operation latency/error
- worker backlog and oldest age
- orphan cleanup count
- range request count and failures

Logs:

- include request id, correlation id, asset id, namespace, owner service, route, outcome
- exclude Blob/SAS URLs, upload targets, raw filenames when unnecessary, file bytes, and secrets

Alerts:

- infected asset in public CMS namespace
- scan backlog critical
- derivative backlog critical for public images
- Blob operation failures
- public download 5xx spike
- orphan object cleanup spike

## Tests

Required tests:

- unknown namespace rejected
- disallowed MIME rejected even when extension is allowed
- MIME spoof rejected
- oversized upload rejected
- completion idempotent with same checksum
- completion conflict with different checksum
- scan pending blocks public/protected download
- infected/failed scan blocks public/protected download
- derivative failure blocks publish when namespace requires derivative
- public grant required for public download
- revoked grant blocks public download
- soft-deleted asset blocks download
- public route returns `404` for denied private asset
- download never returns Blob/SAS URL
- `Content-Disposition` filename is sanitized
- single-range PDF request returns `206` after authorization
- orphan cleanup deletes uncompleted object after grace period
- worker leases prevent double processing

## Acceptance Criteria

- Upload sessions issue narrowly scoped, short-lived upload targets.
- Completion validates size, checksum, detected MIME, namespace, and caller ownership.
- Public CMS assets require scan-clean before public access.
- Image derivatives inherit original asset permissions and route through gateway URLs.
- PDF downloads support safe streaming and planned range behavior.
- Public clients never see Blob URLs, SAS URLs, storage keys, or broad upload credentials.
- Workers are idempotent, lease-based, observable, and retryable.
- Asset pipeline supports weekly PDFs, news/page images, LINE group files, and future desktop-folder objects without embedding their business logic in `asset-api`.
