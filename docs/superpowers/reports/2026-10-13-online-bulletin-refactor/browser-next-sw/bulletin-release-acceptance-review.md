## Follow-up: exact live-reader write preview feasibility

Reviewed the requested restricted action: open existing published issue1742/general/zh-Hant, do not turn pages, highlight or edit notes, preserve current progress. **Do not execute under a promise of “new receipt + same-position progress CAS only”: the implementation cannot guarantee that scope.** This is not a newly introduced defect; it is the existing reader lifecycle.

- POST `/api/member/bulletins/{issueID}/versions/zh-Hant/online/access?series=general` creates/reuses account/document/revision-bound reader receipt and client-request replay records, trace code/privacy version and bounded validation/offline deadlines. It is a real persistence operation even when no content is edited.
- GET `/api/member/bulletins/{issueID}/versions/zh-Hant/online/reader/state?series=general` is not database read-only. Repository ReaderState calls privateReader with nil mutations; it loads/creates state, migrates revision/anchors/conflicts, prunes bounded expired account processed-mutation rows, saves migration/highlight/note/progress state and commits. If old state needs migration, existing annotation mappings/history may legitimately change. Therefore a browser GET allowlist cannot guarantee zero private-data writes.
- POST `/api/member/bulletins/{issueID}/versions/zh-Hant/online/reader/mutations?series=general` writes supplied operations and dedupe receipts. The setProgress branch explicitly rejects BaseVersion; its ordering is CreatedAt >= existing RecordedAt, not optimistic CAS. Even identical position updates timestamps. A visible-page observer can choose the first visible sentence/component rather than the exact prior cloud anchor.
- Initial restore intentionally invokes onPage/onAnchor with record=false, so it does not itself deliberately queue progress. However programmatic scrolling triggers vertical/mobile observers, and exit records visible paper and flushes. No clicks is insufficient assurance against progress writes. Restored local/session position can also take precedence over cloud position.
- When an existing offline save is available, usePrivateReader mounts syncPrivateReplica automatically. Existing queued mutations may replay under their original IDs. A user's reused browser profile may therefore send more than progress without any new edit during smoke.

Safe limits for a concrete preview: use a designated approved test account and isolated profile with no existing offline save/queue/session position; fix issueID/documentID/published revision as observed immediately before test; disclose access/request persistence, private-state initialization/migration/pruning and potential progress/dedupe writes rather than promising CAS or byte-preserved state. Do not clear or alter the user's profile or production account data. If preserving existing annotations/progress exactly is mandatory, stay on list/editor read-only scope and use the synthetic full-Next harness for reader interaction; do not open this live reader. A dedicated test-account live run can be authorized with its actual broader bounded writes, but cannot establish untouched existing-user-state guarantees.

No such live reader request was executed by this reviewer. Coordinator confirmed it has only opened list/editor so far.
