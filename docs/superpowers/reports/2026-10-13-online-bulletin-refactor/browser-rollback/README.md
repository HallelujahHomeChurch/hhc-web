## Exercised actual code and cases

- Seeded 20 copies with original baseline `stageOfflineSave`/`commitOfflineSave` and real checksum-verified font/art bytes. First ten cover valid V1–V10 representatives with supported Hant/Hans mix; remaining ten are expired or explicitly locked. Selector/account/document/revision, resource digests/lengths, identity epoch, access receipt and local/check deadlines were recorded.
- Actual `seedPrivateReplica`, `enqueuePrivateMutation`, `claimPrivateMutation`, `acknowledgePrivateMutation` and CAS-bound `retainReaderRecoveries` operate on browser IndexedDB. Actual return-state save/read semantics operate in the same tab's sessionStorage.
- Baseline queued a partial-range highlight, claimed it, and applied it in the existing `createReaderPreviewStore`; response was deliberately withheld from local acknowledgement. A second baseline note was queued but not sent. Candidate, after an offline read phase, claimed exactly the original highlight ID/payload/timestamp, and the existing preview store deduplicated it: highlight version stayed 1 and the replay response equalled the original. Candidate then sent and acknowledged the original unsent note.
- An independent document held a genuine stale-baseVersion local note edit after a concurrent preview-store edit. PreviewStore's note_conflict exception was explicitly adapted to a synthetic conflict response, acknowledged into the real local queue, and retained with original ID/baseVersion and recoveryReason. Claim remained blocked in candidate and rolled-back baseline. The entire conflict replica stayed byte-for-byte equal; no automatic recovery choice was fabricated.
- Baseline dirty-note return state (including original action, selected range, draft, note ID/baseVersion and savedAt) survived candidate and rollback unchanged. Candidate created a second dirty return for another document, also readable unchanged after rollback.
- Candidate enqueued a new note with fixed original ID/payload/timestamp. Rolled-back baseline read the identical pending record and acknowledged it using the actual claim/ack path. Final main queue was empty only after those explicit acknowledgements; two notes and one once-applied highlight remained.
- For each current V1–V10 save, `readOfflineSave` and `verifyReaderAccess` produced the real renderable input. Actual shared paper renderer plus Ebook rendered into Chromium DOM. All four synthetic sentences and anchors were asserted present; semantic text, fragment attributes, anchors and sentence manifests matched baseline → offline candidate → offline rollback. This is shared-renderer semantic parity, not the full WeeklyReader interaction UI or pixel/font-layout acceptance.
